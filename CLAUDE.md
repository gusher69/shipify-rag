## Project Overview & Goal

**Shipify AI Platform** — an AI customer-service agent that answers customers automatically on **LINE OA**, combining a RAG knowledge base with live ERP data through a configuration-driven integration layer, plus a full Admin Web UI.

```
Customer types in LINE OA
  → FastAPI webhook (line_bot/webhook.py)
  → Intent + sentiment + language detection (line_bot/intent.py)
  → Decision Engine (services/decision_engine.py) routes to:
        - Business Action (ERP API call, via services/action_executor.py)   — live/record data
        - RAG search (rag/searcher.py, Supabase pgvector)                   — policy/FAQ/static content
        - both, combined
  → Tone Engine (line_bot/tone.py) → reply, OR Smart Handoff (LINE Notify) if confidence is low
  → User Profile updated (profiles/manager.py, Supabase Postgres)
```

The **Admin Web UI** (`admin/routes.py`) is the primary day-to-day surface: Knowledge Base management, Business Action ("ERP Integration") configuration with an AI-guided setup wizard, AI Playground, Prompt Studio, AI Policies, Evaluation/Benchmark, and Production Validation.

**Goal**: this is a reusable **AI Platform** with one current deployment (Shipify, import/logistics), not a one-off custom build. See the Platform-First Architecture principle below — it governs every design decision in this repo.

## Architecture

| Layer | Technology | Notes |
|---|---|---|
| Channel | LINE Messaging API v3 | Thai-first, but not hardcoded to Thai |
| AI Model | OpenAI `gpt-4o` / `gpt-4o-mini` (default) | Azure OpenAI / Groq / OpenRouter available as alternate providers — see `services/llm_service.py` |
| Embedding | OpenAI `text-embedding-3-large`, 3072 dims | `services/embedding_service.py`; `EMBEDDING_PROVIDER=local` is a non-default fallback |
| Vector DB | Supabase pgvector | `knowledge_chunks.embedding VECTOR(3072)` — see `migrations/019_openai_embedding_dimension.sql` |
| Relational DB | Supabase Postgres | Business Actions, credentials, user profiles, sync jobs, AI policies, benchmark data |
| File storage | Supabase Storage (default) | pluggable via `storage/` (S3, local disk, Google Drive also supported) |
| Backend | Python 3.13 + FastAPI | no other backend language |
| ERP Bridge | Python wrapper → PHP/MySQL (`erp/bridge.py`) | read-only only, never writes to the customer's ERP |
| Business Action Center | `services/business_action_registry.py`, `services/action_executor.py` | config-driven ERP/API integration registry — the general-purpose replacement for hand-coded per-customer ERP glue |
| AI Auto Setup | `services/ai_auto_setup_service.py` + `admin/templates/business_actions.html` | reads a pasted cURL/Postman/API doc, proposes a full Business Action configuration (parameters, secrets, routing, AI behaviour), reviewed/edited by the admin before saving — never auto-saves |
| Decision Engine | `services/decision_engine.py` | routes each message to ERP vs. RAG vs. both, based on intent + configured routing metadata (not yet the sole router in production — see `docs/CURRENT_STATUS.md`) |
| Credential Store | `services/credential_store.py` | Fernet-encrypted, multi-tenant secret storage for Business Action credentials (separate from the legacy per-variable `secret_configuration` env-var mechanism) |
| Knowledge Manager | FastAPI + Jinja2 | Admin Web UI, server-rendered, vanilla JS (no SPA framework) |
| File sync | Google Drive API + APScheduler | nightly ingestion job, `ingestion/gdrive_sync.py` |
| Hosting target | Railway.app | Supabase is a separate hosted service either way |

### Data Routing Rule (important)
- **Price / stock / order status / anything that changes** → ERP Business Action only — never cached into Supabase as fact.
- **FAQ / policy / how-to / static documentation** → Supabase pgvector (RAG).
- A Business Action's `setup_metadata.routing` field records the intended source preference (ERP only / KB only / ERP first / etc.) generated by AI Auto Setup and editable in the Advanced Editor's Routing tab.

### Confidence & Handoff
- `CONFIDENCE_THRESHOLD` (default `0.75`, `config.py`) — below this, or on a negotiation/complaint keyword, the conversation is escalated via **Smart Handoff** (LINE Notify) instead of auto-replying.
- A handoff message must include: intent, sentiment, retrieved RAG chunks, ERP data (if any), and recent chat history.

### User Segments
- `cold` = never ordered | `warm` = 1–2 orders or spend < ฿5,000 | `hot` = above that.
- Segment logic: `profiles/manager.py:calc_segment()`.

## Coding Conventions

- **Python 3.13**, standard library `unittest` for tests (no pytest-specific syntax) — see `tests/*.py`, run via `python -m unittest discover -s tests`.
- **Server-rendered admin UI**: Jinja2 templates in `admin/templates/`, vanilla JS embedded in `<script>` blocks (see `admin/templates/business_actions.html`) — no build step, no npm project. New UI work should follow this same pattern unless a genuinely new tool is introduced deliberately.
- **Config is centralized** in `config.py` — every environment variable is read there once; other modules import the already-resolved constant, they do not call `os.getenv` directly.
- **Deterministic vs. AI-generated logic must stay separably labeled.** Post-processing added on top of an LLM's output (canonical name inference, confidence scoring, warnings/recommendations, semantic classification) is written as pure, non-LLM functions and commented as such — never silently blur the line between "the AI proposed this" and "we deterministically computed this from what the AI proposed."
- **Never let unreviewed AI output auto-save.** Every AI-generated proposal (Business Action setup, suggested questions, etc.) goes through an explicit Review & Edit step before anything is persisted.
- English for code, comments, and UI labels/helper text; Thai is acceptable (and expected) only for content that is itself customer-facing conversational text (example customer questions, LINE reply templates).

## Important Folders

- `admin/` — Admin Web UI: `routes.py` (main app, ~135 routes), `preview_server.py` (dev-preview variant used by `.claude/launch.json`), `templates/` (Jinja2 + inline JS), `sidebar_config.py` (feature-flag-gated nav).
- `services/` — business logic: Business Action registry/executor, AI Auto Setup, Decision Engine, Credential Store, LLM/embedding abstractions, prompt builder, storage callers. This is where most backend logic lives — prefer adding here over `admin/routes.py` for anything beyond request parsing.
- `rag/` — retrieval pipeline: hybrid (vector + keyword + heading) scoring, query understanding/rewrite, confidence scoring, conversation state, spell correction.
- `ingestion/` — document readers (PDF/Word/Excel) → chunker → embedder → Supabase upsert; Google Drive sync.
- `line_bot/` — the actual customer-facing channel: webhook, intent classifier, tone engine, message adapter.
- `erp/` — read-only ERP bridge; treat as an external system boundary, never assume its schema is Supabase's.
- `migrations/` — hand-written, numbered SQL files (no ORM). Always add the next number; never edit an already-applied migration.
- `tools/` — one-off scripts (seeding, backfill, knowledge-base reset) — safe to run against a dev database, **never run destructive ones against production without confirmation**.
- `tests/` — ~85 `unittest` files; almost every service/rag module has a corresponding test file.

## Main Entry Points

- `admin.routes:app` — the main Admin Web UI + all admin/API routes (production entry point).
- `admin.preview_server:app` — a preview/dev variant of the same app, used by Claude Code's browser-preview tooling (`.claude/launch.json`, port 8001).
- `line_bot.webhook:app` — the LINE Messaging API webhook (separate process/port from the admin app).

## Database & Key Tables

Supabase Postgres + pgvector. No ORM — migrations are plain, numbered `.sql` files in `migrations/`, applied in order. See `docs/DATABASE.md` for the full table list and relationships. Key tables:
- `knowledge_chunks` — RAG vector store (`embedding VECTOR(3072)`), `knowledge_files`/`knowledge_items`/`knowledge_attachments` — source documents and their metadata.
- `business_actions`, `business_action_parameters`, `business_action_parameter_groups`, `business_action_executions` — the Business Action Center registry.
- `credentials` — Credential Store (Fernet-encrypted secret values, multi-tenant).
- `user_profiles` — customer segmentation and chat style.
- `ai_sessions`, `ai_policy_sets`, `rag_benchmark_*` — AI Playground / Prompt Studio / Evaluation support tables.

## Important APIs

See `docs/API.md` for the full endpoint reference. The two API surfaces to know:
1. **Admin API** (`/admin/api/...`, `admin/routes.py`) — everything the Admin UI calls: Business Actions CRUD + AI Auto Setup (`/admin/api/business-actions/ai-auto-setup/*`), Credential Store (`/admin/api/credentials/*`), Knowledge Base, AI Playground, etc. Session-cookie authenticated (`ADMIN_USERNAME`/`ADMIN_PASSWORD`).
2. **LINE webhook** (`POST /webhook`, `line_bot/webhook.py`) — the customer-facing entry point, verified via `LINE_CHANNEL_SECRET`.

## External Services

OpenAI (LLM + embeddings, primary) · Azure OpenAI / Groq / OpenRouter (alternate LLM providers) · Supabase (Postgres, pgvector, Storage) · LINE Messaging API + LINE Notify · Google Drive API (nightly sync) · optional S3-compatible storage · the customer's own ERP (PHP/MySQL, read-only, via `erp/bridge.py`).

## Business Rules

- ERP data (price, stock, order status) is **never** cached as fact into Supabase — always fetched live through a Business Action at answer time.
- A detected secret (API key, token, password-shaped parameter) in a pasted cURL/API doc must **never** be stored in plaintext anywhere — not in Business Action metadata, proposal JSON, logs, toasts, or exported configuration. It goes into the Credential Store (encrypted) or a named environment variable (legacy `secret_configuration`) only.
- AI Auto Setup must never silently convert a form/body secret into an HTTP header (or vice versa) unless the source material explicitly says so — the original transmission location is preserved.
- Confidence below `CONFIDENCE_THRESHOLD`, or a negotiation/complaint signal, always routes to Smart Handoff — never a forced auto-reply.

## Do Not Change Without Necessity

- **Business Action architecture** (registry schema, parameter model, execution model)
- **Provider architecture** (`services/business_action_providers.py`)
- **Action Executor** (`services/action_executor.py`)
- **Decision Engine execution flow** (`services/decision_engine.py`)
- **Credential Store** (`services/credential_store.py`) — encryption scheme, key handling
- **The existing AI Analysis Pipeline** (`services/ai_auto_setup_service.py`'s LLM call/schema) — additive, deterministic post-processing layered on top is fine; changing the prompt/schema itself is not
- **The existing save flow** (`POST /admin/api/business-actions/ai-auto-setup/save` in `admin/routes.py`)

These have been called out explicitly across recent sprints because UI/UX and explainability work sits *on top of* them without needing to touch them — treat that separation as intentional architecture, not an oversight.

## How to Verify Before Editing Code

1. Read the relevant test file(s) in `tests/` first — nearly every service module has one, and it documents the intended behavior better than reverse-engineering the code.
2. `python -m unittest discover -s tests -q` before AND after a change — a pre-existing failure unrelated to your change is fine to note and leave; a new failure is not.
3. For anything touching the Admin UI, verify in a real browser against the running app (`admin.preview_server:app` / `admin.routes:app`) — unit tests do not exercise the JS.
4. For anything touching secrets/credentials, explicitly confirm the raw value never appears in any HTTP response, browser console, or log — grep the response payload, don't assume.
5. Before assuming a migration/table exists, check `migrations/*.sql` — there is no ORM to introspect.

## Engineering Principle: Platform-First Architecture (permanent, effective from AI Core v1.0.1+)

**This project is an AI Platform with ONE current deployment (Shipify), not a one-off custom build.** Every future customer may come from a completely different industry (logistics, insurance, healthcare, manufacturing, retail, banking, government, education, hospitality). Design accordingly:

- **Platform → Configuration → Customer.** Never Customer → Custom Code.
- **Configuration over code.** Anything a second customer might name differently (tracking number, policy number, claim number, booking number, invoice number, patient ID, reservation number) must be a configurable **Identifier Type**, never a hardcoded field name.
- **Business capability, not customer workflow.** Name things by what they DO generically: "Status Inquiry Workflow" not "Shipify Tracking"; "Inventory Location Workflow" not "China Warehouse"; "Case Management Workflow" not "Insurance Claim"; "Entity Status Workflow" not "Order Status."
- **Generic module names.** Prefer "Workflow Engine", "Execution Engine", "Business Action Engine", "Information Collection Engine", "Capability Registry", "Entity Resolver", "Validation Engine" — never "Tracking Engine", "China Import Engine", "Warehouse Engine".
- **ERP abstraction.** Business logic must go through an ERP Adapter Interface and must never know whether the backend is SAP, Oracle, Dynamics, Shopify, WooCommerce, or a custom ERP.
- **Before writing any feature**, evaluate: (1) can another customer use this as-is? (2) can this become configuration? (3) is customer-specific logic leaking into the platform layer? (4) can this scale to 100 customers without a redesign? If any answer is no, redesign first.
- **Every implementation must be presented with**: Platform Components / Customer Configuration / Extension Points / Future Scalability / Technical Debt — BEFORE the code itself.

## Engineering Principle: Architecture Decision & Refactoring Policy (permanent)

The goal of this project is to build a reusable AI Platform, but continuous architectural improvements must not delay delivery. Continuously identify better designs, but always classify a proposed refactor into exactly one category before recommending it:

- **🟥 P0 — Critical**: must be implemented immediately. Security vulnerabilities, data corruption, production failures, broken tests, production-affecting performance issues, bugs causing incorrect business behaviour.
- **🟧 P1 — Required**: required for the current customer. Missing business requirement, current project requirement, integration blocker, required API, required workflow.
- **🟨 P2 — Improvement**: architecture improvements that provide value but are not required for current delivery (better abstraction, cleaner architecture, generic workflow, better naming, improved modularization). Propose these, but they **must NOT interrupt the current implementation**.
- **🟩 P3 — Future Enhancement**: ideas that improve future scalability, multi-tenancy, or future customers (multi-tenant registry, marketplace, plugin system, workflow designer, generic identifier registry, visual workflow builder). These must **NEVER trigger an immediate refactor** — record them as Future Enhancement / Technical Debt and continue implementation.

**Stop Refactor Rule**: if the current implementation satisfies business requirements, AND tests are passing, AND production quality is acceptable — freeze the implementation. Do not redesign it only because a more generic solution exists.

**Technical Debt format**: when identifying a future improvement, do not recommend implementing it immediately — produce a Technical Debt entry instead, with Title / Reason / Business Value / Estimated Complexity / Suggested Timing.

**Feature Completion**: mark a feature Production Ready when business requirements are satisfied, regression tests pass, architecture is acceptable, and documentation is complete — then move to the next feature.

**Output Policy**: every implementation concludes with (1) Production Status, (2) Technical Debt, (3) Future Enhancements, (4) Recommended Next Task. Only recommend refactoring when the issue is classified P0 or P1 — otherwise continue with the roadmap.

**Objective**: ship a stable, reusable AI Platform — not continuously redesign completed modules. Prefer Deliver → Validate → Improve Later, never Design → Redesign → Redesign Again → Never Ship.
